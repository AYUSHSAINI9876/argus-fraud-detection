# Model Card — Argus Risk Engine

Following the [Model Cards for Model Reporting](https://arxiv.org/abs/1810.03993)
framework. Numeric results are regenerated by `python -m argus_ml.train` and
written to `ml/artifacts/evaluation.json`; nothing in this file is hand-copied
from a run that is no longer reproducible.

---

## Model details

| | |
|---|---|
| **Developed by** | Ayush Kumar Saini |
| **Model type** | Gradient-boosted decision trees (XGBoost), isotonic/Platt-calibrated |
| **Version** | v1 |
| **Input** | 58 engineered numeric features derived from one transaction plus the customer's preceding 7 days of activity |
| **Output** | Calibrated P(fraud) ∈ [0, 1] |
| **Companion models** | Logistic regression (baseline + challenger), multivariate Gaussian anomaly detector (unsupervised layer) |
| **Licence** | MIT |

### Why this architecture

Gradient-boosted trees remain state of the art on tabular fraud. On ~60
engineered numeric features with mixed scales and heavy interactions, they beat
deep learning on accuracy, training cost, and inference latency
simultaneously. Deep learning wins on sequences and text; this is neither.

---

## Intended use

**Intended:** Real-time risk scoring of card transactions, producing a
calibrated probability that feeds an expected-cost decision policy and an
analyst review queue.

**Intended users:** Fraud analysts working a case queue; risk managers tuning
policy; ML engineers monitoring drift.

### Out of scope

- **Not a standalone decision-maker.** The score feeds a policy with human
  review in the loop. Nothing about the model justifies removing that loop.
- **Not a credit or eligibility model.** It estimates the probability that a
  specific transaction is fraudulent — not creditworthiness, and not anything
  about the person.
- **Not trained on real transaction data.** See Limitations.
- **Not validated for regulatory submission.** A production deployment would
  require model risk validation, fair-lending review where applicable, and
  documented governance sign-off. None of that has been done.

## Training data

Synthetically generated (`argus_ml.data.generator`). Public fraud datasets are
PCA-anonymised (`V1..V28`), which makes meaningful feature engineering
impossible and leaves nothing an analyst UI can explain — so the project
generates its own stream instead.

**Population:** 1,200 merchants across 10 metropolitan areas
(US, GB, DE, IN, SG, AE, BR). The generator defaults to 8,000 customers × 180
days; **the shipped artefacts in `ml/artifacts/` were trained at 5,000
customers × 120 days**, producing 806,945 transactions. Every figure quoted
below comes from that run.

**Legitimate traffic** is modelled per-customer: a persistent lognormal spend
profile, a home location, preferred merchant categories, a Poisson transaction
rate, and a diurnal activity curve. 92% of activity occurs near home; the
remainder is travel.

**Fraud** is injected as *episodes* on ~3.5% of customers, producing a
measured transaction-level fraud rate of **0.173%** (1,393 of 806,945). That
sits below the 0.3–0.7% usually quoted for card portfolios, so the positive
class here is *thinner* than a real one, not more generous. Raising
`fraud_episode_rate` is the knob if a denser positive class is wanted.

### Fraud typologies

| Typology | Share | Signature |
|---|---|---|
| Card testing | 26% | 6–22 micro-charges minutes apart, new device |
| Account takeover | 22% | New device + new country, escalating amounts |
| CNP burst | 20% | 3–11 mid-size e-commerce charges within an hour |
| Geo-velocity | 14% | Physically impossible travel, magstripe fallback |
| Bust-out | 11% | Slow build over days toward the credit limit |
| Structuring | 7% | Repeated transfers pinned just under $10,000 |

### Label timing

Each fraud label carries a `label_timestamp` drawn from N(21, 9) days, clipped
to [1, 120] — modelling chargeback reporting delay. At the training cut-off,
fraud whose chargeback had not yet arrived is masked to negative. Training
without this is the subtlest form of leakage in fraud and produces offline
numbers production never reproduces.

## Evaluation

**Protocol:** strictly temporal split (60% train / 15% validation / remainder
test) with a **7-day embargo** between splits, so 7-day velocity windows cannot
straddle a boundary.

**Why not a random split:** fraud is bursty and episodic — one compromised card
produces a cluster of correlated transactions within minutes. A random split
scatters that cluster across train and test; the model memorises the episode
and the test score inflates, in practice by 20+ PR-AUC points.

### Metrics reported, and why

| Metric | Why it is here |
|---|---|
| **PR-AUC** | Headline. The honest summary at a 0.2% positive rate |
| ROC-AUC | Comparability with published baselines only — it flatters every model at this class balance |
| Brier, ECE | The policy consumes probabilities; miscalibration corrupts every decision downstream |
| Precision @ analyst capacity | The operating point a real fraud team lives at |
| Recall @ analyst capacity | What that operating point actually catches |
| **Recall per typology** | An aggregate of 0.70 can hide an attack type caught 0% of the time |
| Net savings / 1k txn | Fraud prevented, less friction cost, less analyst time |

Metrics deliberately **not** reported as headline figures: accuracy (predicting
"never fraud" scores 99.8%) and F1 at a 0.5 threshold (nobody operates there at
this base rate).

### Results

Test window: 107,685 transactions, 216 fraud (0.201%).

| Model | PR-AUC | ROC-AUC | Brier | ECE | P@cap | R@cap | Savings/1k |
|---|---|---|---|---|---|---|---|
| Logistic baseline | 0.8932 | 0.9931 | 0.00400 | 0.0076 | 0.3829 | 0.9537 | $689.26 |
| **XGBoost (calibrated)** | **0.9720** | 0.9961 | 0.00013 | 0.0001 | 0.3922 | 0.9769 | **$708.01** |
| XGBoost (uncalibrated) | 0.9720 | 0.9961 | 0.00013 | 0.0002 | 0.3922 | 0.9769 | $708.01 |
| Gaussian anomaly | 0.0486 | 0.8112 | 0.60261 | 0.7277 | 0.0645 | 0.1620 | $553.95 |
| Ensemble (0.85/0.15) | 0.9588 | 0.9759 | 0.01368 | 0.1092 | 0.3866 | 0.9630 | $705.25 |

Recall by typology at analyst capacity (XGBoost): account takeover, card
testing, CNP burst, geo-velocity and structuring all 1.000; **bust-out 0.828**
(logistic 0.690). Bust-out is the standing weakness — per-transaction features
cannot see a multi-day trajectory.

**The ensemble is not promoted.** It loses to the champion on PR-AUC
(0.9588 vs 0.9720) and is three orders of magnitude worse calibrated
(ECE 0.1092 vs 0.0001), because averaging in a 0.049-PR-AUC signal dilutes a
0.972 one. The anomaly detector remains a parallel review-routing signal, not
a component of the champion score.

See `ml/artifacts/evaluation.json`, regenerated on every training run. The CI
pipeline additionally enforces that the XGBoost champion beats the logistic
baseline on PR-AUC, failing the build otherwise.

## Calibration

Raw XGBoost outputs are skewed high because `scale_pos_weight` reweights the
loss for class imbalance. Since the decision policy computes expected cost from
the score, that skew would corrupt every decision. A calibrator is fitted on a
disjoint temporal slice the booster never saw.

**Method selection by positive count** — ≥500 positives uses isotonic, below
that uses Platt scaling. This threshold exists because of a bug found during
development: with too few positives, isotonic degenerates into a near-constant
step function, collapsing thousands of distinct scores onto a handful of values
and destroying ranking resolution — even though the transform is technically
monotone. Platt scaling has two parameters and cannot tie scores.

The shipped model calibrated with **Platt** (258 positives in the calibration
slice, below the 500 threshold), on a booster that early-stopped at iteration
186 with `scale_pos_weight = 870.4`.

### What calibration actually bought, measured

Aggregate Brier and ECE barely separate the calibrated model from the raw one
(0.00013/0.0001 vs 0.00013/0.0002). That is **not** evidence that calibration
was unnecessary — it is an artefact of count-weighting. 99.79% of test rows
land in the lowest score bin, where both models are already exact, and that bin
dominates any count-weighted average.

The effect is in the bins where decisions are made:

| Score bin | Calibrated gap | Raw gap |
|---|---|---|
| [0.93, 1.00) | 0.0028 | 0.0076 |
| [0.87, 0.93) | 0.1001 | 0.0920 |
| [0.80, 0.87) | 0.0661 | 0.1577 |

The honest reading: calibration helps in the high-score region that drives
blocks, the improvement is smaller than the "raw XGBoost outputs are badly
skewed" story predicts, and a single aggregate ECE is the wrong instrument for
seeing it at this base rate. Reliability is therefore reported per bin.

## Ethical considerations

**A false positive is a real harm.** Blocking a legitimate transaction can mean
a declined card at a checkout, a failed rent payment, or a stranded traveller.
The system reflects this in three places: the expected-cost policy prices false
positives explicitly; `min_block_score` prevents auto-blocking on weak evidence
regardless of the arithmetic; and every block is reviewable, with release
gated to REVIEWER and written to the audit log.

**Explainability is a requirement, not a feature.** Every decision carries SHAP
attributions surfaced in the analyst UI, so a human can state why a transaction
was flagged. A risk platform that cannot answer "why" is not deployable.

**Proxy discrimination is a live risk.** Features such as
`distance_from_home_km`, `is_foreign_country`, and merchant category can
correlate with nationality, immigration status, or socioeconomic position. A
production deployment **must** run slice analysis across protected
characteristics before launch. The synthetic generator has no demographic
attributes, so that analysis cannot be run here — this is a stated gap, not a
clean bill of health.

**The unsupervised layer needs its own scrutiny.** Anomaly detection flags
"unlike the majority", which for a customer whose legitimate behaviour is
genuinely atypical — frequent international travel, irregular income, an
unusual spend pattern — means systematically more friction. This is why the
anomaly score routes to *review* rather than *block*.

## Limitations

1. **Synthetic training data.** The generator encodes my model of fraud. Real
   portfolios contain patterns nobody has thought to simulate — which is
   exactly why the unsupervised layer exists, and exactly why no claim is made
   here about real-world performance.
2. **No demographic fairness analysis.** Cannot be performed on data that has
   no demographic attributes. Stated as a gap.
3. **Cold start.** A customer's first transaction has no velocity history. The
   model receives explicit sentinel values and an `is_first_transaction` flag
   rather than NaN, but genuinely has less to work with.
4. **Concept drift is adversarial.** Fraud models decay faster than most,
   because the opponent adapts. Drift monitoring (PSI) is implemented; note
   that retraining on drifted data is not automatically correct — if the drift
   *is* the attack, retraining teaches the model the attack is normal. The
   retraining trigger therefore returns a recommendation with a reason, and
   promotion still requires a human.
5. **Single-region state.** A customer transacting across regions would have
   divergent velocity windows.

## Maintenance

| | |
|---|---|
| **Retraining trigger** | Drift-based (PSI), not scheduled |
| **Promotion gate** | Must beat the incumbent on PR-AUC on a temporal holdout; enforced in CI |
| **Monitoring** | Data drift, prediction drift, realised precision from analyst dispositions, p95/p99 latency |
| **Shadow evaluation** | The challenger scores all live traffic; its decisions are logged, never acted on |
| **Rollback** | `POST /admin/models/promote` reloads from disk and re-runs the feature-contract assertion before swapping; a failed validation rolls back automatically |
